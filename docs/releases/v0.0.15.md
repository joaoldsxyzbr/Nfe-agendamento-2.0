# NFe Agendamento 2.0 — v0.0.15

Release de consolidação arquitetural, segurança operacional e refinamento da interface construída sobre a v0.0.14.

## Principais mudanças

- interface principal refinada para uso interno, com superfícies planas, menos efeitos decorativos, hierarquia mais clara e consulta visualmente prioritária;
- branding, resultado da consulta, lote, configurações e ações do DANFE simplificados sem alterar os fluxos funcionais;
- fluxo de consulta unitária extraído para um controlador dedicado, reduzindo responsabilidades de `main.ts`;
- fluxo de lote extraído para controlador próprio, preservando processamento sequencial, fallback Portal e downloads;
- seleção de certificado/estado do Bridge e ciclo do visualizador DANFE isolados em controladores testáveis;
- fronteiras do frontend documentadas e cobertas por testes de regressão;
- identificação de fornecedores por CNPJ/CPF resolvida somente no Bridge local, sem publicar identificadores fiscais reais no bundle, documentação ou logs;
- suporte à normalização de CNPJ alfanumérico nas regras locais de fornecedor, com fallback de nome durante a migração;
- coordenador fiscal Cloudflare protegido por rate limiter HTTP antes do Durable Object;
- CodeQL adicionado para análise estática de JavaScript/TypeScript e C#;
- Dependabot configurado para npm, Playwright, NuGet e GitHub Actions;
- ajustes no DANFE e mapeamento de produtos preservados com regressão A4 automatizada;
- infraestrutura de CI e lockfiles restaurados após uma alteração visual externa que havia removido acidentalmente dependências, testes e controladores.

## Arquitetura

A arquitetura funcional permanece a mesma:

- site Cloudflare para interface, parsing XML, DANFE, lote e regras de apresentação;
- App/Bridge local em cada PC;
- Bridge somente em `127.0.0.1:17345`;
- certificado A1 e chave privada permanecem no Windows;
- Worker/Durable Object remoto usado somente para coordenar o consumo fiscal entre PCs;
- helper Portal/WebView2 usado para fallback com hCaptcha manual.

Não existem Central, pareamento, LAN, mDNS ou pasta compartilhada na arquitetura atual.

## Interface

A v0.0.15 reduz o excesso visual introduzido durante a experimentação de UI:

- fundo escuro plano;
- cards com bordas discretas e raios menores;
- azul reservado às ações principais;
- amarelo usado como estado/aviso, não como decoração;
- certificado visualmente secundário em relação à consulta;
- branding mais compacto;
- lote e painel de configurações com densidade maior;
- estados de sucesso, espera e erro continuam semanticamente diferenciados.

Nenhuma dessas mudanças altera a lógica de consulta, certificado, Bridge, Portal, DANFE ou coordenação fiscal.

## Segurança e comportamento fiscal

- Bridge somente loopback;
- Host/Origin continuam validados;
- nenhuma repetição fiscal automática após erro ambíguo ou limite;
- fallback Portal mantém hCaptcha manual;
- XML retornado é validado contra a chave consultada;
- PFX, senha e chave privada não saem do Windows;
- resolução de fornecedor acontece no Bridge local;
- o coordenador remoto não recebe chave NF-e, XML, PFX, senha ou chave privada;
- indisponibilidade ou resposta inválida do coordenador continua falhando de forma conservadora.

## Validação automatizada

A publicação desta release depende do mesmo SHA concluir com sucesso:

- `web`;
- `danfe-print`;
- `bridge`;
- `fiscal-compatibility`;
- `windows-package`.

O CodeQL também é verificado separadamente. O workflow de release publica somente os artifacts gerados pelo CI verde daquele mesmo SHA.

## Validação física ainda pendente

A release pode ser produzida pelo repositório, mas não deve ser declarada fisicamente validada sem executar em ambiente real:

- `docs/testing/acceptance.md`;
- `docs/testing/batch-query.md`;
- `docs/testing/danfe-layout.md`;
- `docs/testing/portal-post-hcaptcha.md`.

O CI não consegue provar comportamento de impressora/driver específico, interação real com certificado A1, SEFAZ ou hCaptcha.

Não provoque bloqueio `656` artificialmente para testar fallback.

## Controles externos ainda pendentes

- Authenticode depende de certificado real de code signing e secrets correspondentes;
- proteção administrativa da `main` depende de ruleset/branch protection configurado no GitHub.

## Atualização

A atualização a partir da v0.0.14 é suportada pelo atualizador manual da bandeja. O Setup continua por usuário, sem necessidade de administrador, e preserva configurações em `%LOCALAPPDATA%\NfeAgendamentoBridge`.

O commit marcador desta release usa exatamente:

```text

```
