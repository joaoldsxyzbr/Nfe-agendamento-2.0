# Design — NFe Agendamento 2.0 v0.0.4

Data: 2026-09-08

## Objetivo

Corrigir com cautela as falhas de confiabilidade identificadas após a validação física da `v0.0.3`, mantendo intacta a lógica fiscal, o tratamento Fernando Klein e o layout/DANFE já aprovados.

## Escopo aprovado

A `v0.0.4` deve corrigir somente:

1. fluxo de instalação/configuração da origem HTTPS;
2. dependência de múltiplas instâncias do Bridge;
3. timeouts inadequados no cliente web;
4. detecção otimista do WebView2 Runtime;
5. cobertura de regressão, CI, documentação e release correspondentes.

Ficam fora de escopo desta revisão:

- protocolo fiscal e regras de `NFeDistribuicaoDFe` além de ajustes estritamente necessários para timeout;
- parser XML;
- tratamento Fernando Klein;
- DANFE e seu layout;
- consulta em lote;
- login, banco, Central, pareamento ou pasta compartilhada;
- updater automático do Bridge.

## Origem oficial

A origem oficial do site é fixa:

```text
https://nfeagendamento.joaolds.xyz.br
```

O usuário final não deve configurar essa origem manualmente.

### Regras

- o instalador não deve exibir tela solicitando URL/origem;
- o Bridge deve iniciar já autorizado somente para a origem acima em produção;
- não usar wildcard;
- manter `127.0.0.1:17345` como Host esperado;
- manter fail-closed para outras origens;
- desenvolvimento pode continuar usando configuração específica de desenvolvimento sem ampliar a produção.

## Instalador Windows

O Setup permanece Inno Setup, por usuário, sem administrador.

Fluxo esperado:

```text
Avançar → Instalar → Concluir
```

O Setup deve:

- instalar em `%LOCALAPPDATA%\NFe Agendamento Bridge`;
- não pedir UAC/admin;
- manter Bridge + Portal helper lado a lado;
- usar publish self-contained `win-x64`;
- criar atalho no Menu Iniciar;
- registrar auto-start em `HKCU`;
- iniciar o Bridge ao concluir quando a opção estiver marcada;
- embutir a origem oficial sem pergunta ao usuário;
- preservar a seleção local do certificado;
- não criar serviço, tarefa agendada, regra de firewall ou updater.

## Instância única do Bridge

O Bridge deve ter proteção de instância única por usuário/sessão.

Comportamento:

- primeira execução inicia normalmente e escuta em `127.0.0.1:17345`;
- uma segunda execução deve encerrar de forma limpa sem tentar subir outro servidor na mesma porta;
- clicar no atalho quando o auto-start já estiver ativo não deve gerar erro visível nem processo duplicado persistente;
- a proteção não deve impedir PCs diferentes nem usuários diferentes de executar seus próprios Bridges.

Implementação recomendada: `Mutex` nomeado por usuário/aplicação, adquirido antes de iniciar o host ASP.NET Core e mantido até o encerramento do processo.

## Timeouts do cliente web

O timeout único de 2 segundos é inadequado para todas as operações.

Separação desejada:

- `health`: curto, ~2 s;
- listagem/seleção de certificado: curta, poucos segundos;
- consulta NF-e: compatível com o transporte do Bridge, com margem sobre os 45 s atuais da SEFAZ;
- Portal fallback: sem timeout global curto; manter polling/cancelamento próprio.

A intenção é evitar que uma consulta SEFAZ válida seja abortada pelo navegador antes do timeout configurado no Bridge.

## WebView2 Runtime

O campo `webView2Available` não deve indicar disponibilidade somente porque `NfeAgendamento.Portal.exe` existe.

A detecção deve representar a capacidade real de abrir o helper:

- helper Portal precisa existir;
- Microsoft Edge WebView2 Runtime precisa estar disponível;
- falhas de detecção não devem impedir a consulta normal via SEFAZ;
- ausência de WebView2 deve afetar apenas o fallback Portal e ser comunicada de forma explícita.

A detecção deve ser implementada sem abrir uma janela do Portal durante o health check.

## Segurança

Preservar os controles existentes:

- Bridge somente em loopback;
- Host estrito `127.0.0.1:17345`;
- CORS/origin allowlist sem wildcard;
- chave privada permanece no Windows;
- helper Portal restrito ao host oficial;
- hCaptcha sempre manual;
- downloads externos bloqueados;
- nenhum retry fiscal automático após falha ambígua.

## Testes

A implementação deve seguir TDD, criando regressões antes das correções.

Cobertura mínima:

1. instalador não contém `CreateInputQueryPage` para origem e contém somente a origem oficial;
2. auto-start, atalho e pós-instalação iniciam o Bridge sem argumento manual de origem;
3. produção aceita `https://nfeagendamento.joaolds.xyz.br` e rejeita outras origens;
4. segunda instância do Bridge é recusada/encerrada de forma limpa;
5. `health` usa timeout curto;
6. `lookupNfe` usa timeout longo compatível com SEFAZ;
7. Portal fallback não herda o timeout curto de health;
8. `webView2Available` é falso quando helper existe mas Runtime não está disponível;
9. ausência de WebView2 não quebra health, certificados nem consulta normal;
10. suíte completa web + Bridge continua verde.

## CI e release

A `v0.0.4` deve:

- manter `npm run test:web`;
- manter `npm run build:web`;
- manter `npx wrangler deploy --dry-run`;
- rodar testes Bridge completos;
- compilar Bridge e Portal helper;
- publicar ambos self-contained `win-x64`;
- compilar o Inno Setup real em runner Windows;
- gerar `NFeAgendamentoBridge-Setup-v0.0.4.exe`;
- gerar `NfeAgendamentoBridge-win-x64.zip` como fallback técnico;
- publicar release apenas se todos os jobs do mesmo commit final estiverem verdes.

A `v0.0.3` não deve ser sobrescrita.

## Documentação

Atualizar no mesmo ciclo:

- `README.md`;
- `docs/architecture/bridge-security.md`;
- `docs/testing/acceptance.md`;
- notas da `v0.0.4`;
- fechamento técnico da versão.

A documentação deve deixar explícito que o usuário não configura mais a origem manualmente.

## Critério de conclusão

A parte automatizável só pode ser considerada concluída quando:

- todos os testes novos passam;
- todas as regressões anteriores passam;
- web/build/dry-run passam;
- Bridge/builds passam;
- Windows package gera o Setup real;
- release `v0.0.4` é publicada apontando para o mesmo SHA validado.

A aceitação física continua necessária em Windows real para confirmar instalação, auto-start, A1 real, SEFAZ e fallback Portal/hCaptcha.
